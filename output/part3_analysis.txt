============================================================
5.1 Task 3.1: Conflict Analysis
============================================================

Grammar A (expression grammar, input/grammar.txt):
Expr -> Expr + Term | Term
Term -> Term * Factor | Factor
Factor -> ( Expr ) | id

Observed:
- SLR(1): No conflicts found. Grammar is SLR(1).
- LR(1): No conflicts found. Grammar is LR(1).
- Both parsers accept: id + id * id

Grammar B (LR(1)-but-not-SLR, input/grammar_lr1_not_slr.txt):
Start -> Lhs = Rhs | Rhs
Lhs -> * Rhs | id
Rhs -> Lhs

Observed:
- SLR(1): Conflicts detected. Grammar is NOT SLR(1).
  Conflict reported:
  State I2, symbol '=': shift/reduce conflict (existing=r2, incoming=s8)
- LR(1): No conflicts found. Grammar is LR(1).
- Parsing input "id = id":
  - SLR parser is skipped due to conflicts.
  - LR(1) parser accepts successfully.

How LR(1) resolves the SLR conflict:
- SLR reductions are triggered by FOLLOW sets, which can over-approximate valid lookaheads.
- LR(1) uses item-specific lookaheads [A -> alpha ., a], so reduce actions apply only for the exact lookahead terminal.
- This extra precision removes the false shift/reduce ambiguity in Grammar B.

  - LR(1) ACTION=22, GOTO=9, estimated-bytes=1664

  - LR(1) automaton=0.452462 ms, LR(1) table=0.085671 ms
- Parsing speed (2000 runs, input "id = id"):
  - SLR: not measured (parser disabled due to conflicts)

Performance conclusion:
- LR(1) is generally larger (more states and table entries) and can take more time to construct.
- SLR(1) is usually smaller/faster but may fail on grammars that LR(1) can parse.
- LR(1) provides stronger coverage/precision at the cost of larger parser artifacts.
